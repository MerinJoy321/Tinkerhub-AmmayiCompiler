# AMMAYI.EXE — BACKEND ARCHITECTURE & BUILD PLAN

Scope: backend only. Frontend/UX is being built separately in Google Stitch, so this document
makes zero visual/UX decisions. Everything here exists to feed a JSON API that any frontend
can consume: run code, get a classified error, get an Ammayi response + audio + updated state.

This is written to be handed to Kiro IDE in ordered chunks (see Section 10).

> **Amendment (v1.1):** Added §16, "Ammayi Expression Mapping" — a small, derived,
> presentation-only field (`expression`) added to every Ammayi response, for the frontend's
> 4 static character images. No architecture changed: anger engine, persistence, execution,
> error classification, session/escape logic, and response selection are all untouched.
> Affected sections: §4 (schema), §10 (API contract), §13 (build order), §14 (superseded bullet).

## 1. TECH STACK (per AGENTS.md §27)

- **Framework**: FastAPI (Python 3.11+)
- **Execution**: `subprocess` (never `exec()` in-process)
- **Persistence**: SQLite (single file, `database/ammayi.db`)
- **Response library**: static JSON (`data/ammayi/responses.json`), loaded into memory at startup
- **Audio**: pre-recorded `.wav` files served as static assets, referenced by path only
- **No AI, no LLM, no cloud** — matches AGENTS.md §33

## 3. DATA MODEL (SQLite)

### 3.1 `ammayi_state` — single persistent row (id = 1)

memory the backend owns, which is *stronger* for the product concept than per-user
accounts: no matter what the client clears (cookies, localStorage, incognito), the
backend still remembers everything. This is what makes "there is no escape" literally true.

## 4. RESPONSE LIBRARY SCHEMA (`data/ammayi/responses.json`)

Extends the AGENTS.md §17 example with a couple of extra optional fields needed for
scoring in §8.

```json
{
  "id": "R015",
  "text_ml": "പേര് പോലും ഉറപ്പാക്കിയിട്ടില്ല. പിന്നെ എന്തിനാ വിളിക്കുന്നത്?",
  "audio": "assets/audio/ammayi/R015.wav",
  "error_types": ["NameError"],
  "situations": ["first_time_error", "generic"],
  "anger_range": [0, 3],
  "styles": ["sarcastic", "dry"],
  "priority": 10,
  "min_streak": 0,
  "min_escape_attempts": 0,
  "event_types": ["ERROR"],
  "expression": null
}
```

Field notes:
- `error_types`: `["ANY"]` for non-error events (SUCCESS, ESCAPE_ATTEMPT, EXCUSE, MAKE_IT_WORSE) or generic fallback lines.
- `situations`: tag vocabulary defined in §5.2. A response can match on situation alone even with `error_types: ["ANY"]`.
- `event_types`: which of the six event types this line is eligible for. Lets you keep one JSON file for everything instead of separate files per event.
- `min_streak` / `min_escape_attempts`: optional gating; response is only a candidate if current value ≥ this.
- `anger_range`: inclusive `[min, max]` on the 0–8 anger **level** (not raw score — see §7).
- `expression`: optional, one of `unimpressed` / `disappointed` / `furious` / `done`. Omit or set `null` for the overwhelming majority of lines — only set this when a specific recorded line's performance doesn't match what its anger level would normally imply (e.g. a deliberately quiet, deadpan line delivered at a lower anger level than `done` would usually require). See §16.

### 4.1 Coverage plan for ~20–30 recorded lines

Given the small library, prioritize breadth over depth:

| bucket | suggested count |
|---|---|
| generic error fallback, spread across anger levels 0/2/4/6/8 | 6–8 |
| NameError specific (most common beginner error) | 2–3 |
| SyntaxError specific | 2 |
| TypeError specific | 2 |
| ZeroDivisionError specific | 1–2 |
| "same mistake again" (any error_type, situation=`exact_repeat`) | 2 |
| SUCCESS (spread across low/mid/high anger) | 3 |
| NEW_SESSION / ESCAPE_ATTEMPT (first escape) | 2 |
| ESCAPE_ATTEMPT repeated (situation=`repeated_escape`) | 1–2 |
| EXCUSE dismissal | 2 |
| MAKE_IT_WORSE | 2 |
| one proverb-tagged line, high anger only | 1–2 |

Every error type NOT explicitly covered falls back to the generic bucket — this is why the
generic bucket needs to be the largest one. Tell your teammate this bucket is the highest
leverage set of lines to record well.

## 5. ERROR CLASSIFICATION

### 5.1 Execution → classification pipeline

1. Run code via `execution_engine` (see §9), get `(stdout, stderr, returncode, timed_out)`.
2. If `returncode == 0` and no stderr → `SUCCESS`.
3. If `timed_out` → treat as its own pseudo-error type `TimeoutError` (bucket into generic).
4. Else parse `stderr`'s last non-empty line, typically `SomeException: message`.
   Extract exception class name via regex: `^([A-Za-z_][A-Za-z0-9_]*):`
5. Map extracted class name to MVP set (AGENTS.md §13): `NameError, TypeError, SyntaxError,
   AttributeError, IndexError, KeyError, ValueError, ZeroDivisionError, RecursionError`.
   Anything else → generic `Exception`.
6. Compute `error_signature = sha1(error_type + ":" + normalized_message)`, where
   normalized_message strips variable names/line numbers where feasible (best-effort;
   doesn't need to be perfect — it's just used to detect "literally the same mistake again").

### 5.2 Situation tags (attached to the event before scoring)

Computed by `error_classifier.py` + `state_manager.py` together:

- `first_time_error` — this exact `error_type` has never occurred in state before
- `repeated_error_type` — this `error_type` has occurred before (not necessarily consecutively)
- `exact_repeat` — `error_signature == last_error_signature`
- `rapid_repeat` — `now - last_event_at < RAPID_THRESHOLD_SECONDS` (config, suggest 12s) and last event was also ERROR
- `long_streak` — `current_failure_streak >= LONG_STREAK_THRESHOLD` (config, suggest 5)
- `generic` — always included as a fallback tag on every event so generic-bucket responses are always eligible

For non-ERROR events, situation tags are simpler and mostly just the event name itself:
`success`, `escape_attempt`, `repeated_escape` (if `escape_attempts > 1` after increment),
`excuse`, `make_it_worse`.

## 6. SESSION & ESCAPE DETECTION

### 6.1 Identity model

No login. The frontend is responsible for persisting a `session_id` (e.g. in
localStorage) and sending it on every request after the first. The backend's job is to
notice when that continuity breaks.

`POST /api/session/start` logic:

```text
input: existing_session_id (nullable)

if existing_session_id is provided AND exists in `sessions` table:
    → RESUME. No escalation. Return existing state as-is.
    (this covers plain page refresh / reconnect)

else:
    → this is a NEW session_id (client had none, or sent one we don't recognize)
    new_session_id = uuid4()
    insert into sessions
    total_sessions += 1

    if total_sessions_before_this_increment > 0:
        # i.e. this is NOT the very first session this backend has ever seen
        → ESCAPE_ATTEMPT event
        escape_attempts += 1
        mark this session is_escape_attempt = true
        run through anger_engine (delta depends on whether this is a repeat escape, §7)
        select an ESCAPE_ATTEMPT response (repeated_escape tag if escape_attempts > 1)
    else:
        # genuinely the first time this backend has ever been talked to
        → no escalation, no response payload beyond the neutral opening state
```

Optional (nice-to-have, not required): accept a coarse `client_fingerprint` (e.g. hash of
user-agent) purely for the stats panel / demo flavor — do **not** use it to try to
re-identify users across cleared storage; that's a rabbit hole not worth hackathon time.
The backend-owned single-memory model in §3.1 already makes escape impossible by design,
which is the actual joke — lean into that rather than building real device fingerprinting.

## 7. ANGER ENGINE

### 7.1 Score vs. Level

- `anger_score`: raw integer, accumulates per event, **never decreases**, capped at
  `MAX_ANGER_SCORE = 20` (tune as needed) purely so it doesn't grow unbounded in storage/stats.
- `anger_level`: derived bucket (0–8) computed from `anger_score`, per AGENTS.md §31:

```text
score 0        → 0  CALM
score 1–2      → 1  UNIMPRESSED
score 3–4      → 2  SUSPICIOUS
score 5–6      → 3  DISAPPOINTED
score 7–8      → 4  ANNOYED
score 9–10     → 5  ANGRY
score 11–12    → 6  FURIOUS
score 13–14    → 7  AMMAYI RAGE
score 15+      → 8  INCENSED
```

`response.anger_range` in the JSON library is checked against `anger_level`, not raw score.

### 7.2 Event deltas

Per AGENTS.md §31, with the ambiguity resolved as: bonuses are **additive on top of the
base +1 for an error**, but the whole thing is capped per single event so one error can't
spike anger too hard.

```text
base_delta(ERROR)            = +1
  + exact_repeat bonus        +1   (so exact repeat error = +2 total)
  + rapid_repeat bonus         +1  (so rapid + exact repeat = +3 total, capped below)
  cap per single ERROR event to +3 max

SUCCESS                       = +0   (never decreases anger — locked, AGENTS.md §16)
NEW_SESSION (not escape)      = +0
ESCAPE_ATTEMPT (first ever)   = +3
ESCAPE_ATTEMPT (repeated,
  escape_attempts > 1)        = +5
EXCUSE                        = +1
MAKE_IT_WORSE                 = +1
```

`highest_anger = max(highest_anger, anger_score)` updated on every event.

### 7.3 Streak tracking

- `current_failure_streak += 1` on ERROR, reset to `0` on SUCCESS.
- `longest_failure_streak = max(longest_failure_streak, current_failure_streak)`.

## 8. RESPONSE ENGINE (selection algorithm)

Given an event with `event_type`, `error_type` (nullable), `situations: set[str]`,
`anger_level`, `current_streak`, `escape_attempts`:

```text
candidates = [r in library if event_type in r.event_types]

for each candidate r, compute score:
    score = 0
    if error_type is not None:
        if error_type in r.error_types: score += 30
        elif "ANY" in r.error_types: score += 10   # generic fallback still eligible, lower weight
    else:
        if "ANY" in r.error_types: score += 30      # non-error events always match ANY

    if any(tag in r.situations for tag in situations): score += 30

    if r.anger_range[0] <= anger_level <= r.anger_range[1]: score += 20
    else: score -= 100   # hard filter: never select a response outside its anger range

    if r.min_streak <= current_streak: score += 10
    else: score -= 100   # hard filter

    if r.min_escape_attempts <= escape_attempts: score += 5
    else: score -= 100   # hard filter

    score += r.priority   # small tie-break nudge, author-controlled

    # anti-repetition
    if r.id == state.last_response_id: score -= 50
    usage = response_usage[r.id]
    if usage.last_used_session_id == current_session_id: score -= 15

pick candidate with max(score); break ties randomly among top scorers
if best_score < MIN_ACCEPTABLE_SCORE (config, suggest 30):
    fall through to fallback tiers below
```

### 8.1 Fallback tiers (guarantee a response always exists)

1. Same scoring, but drop the anger-range hard filter (keep it as a soft +20 instead) — closest anger match still wins.
2. Drop situation matching requirement entirely, keep only `error_type`/`ANY` + event_type match.
3. Pure generic bucket: any response tagged `generic` for this `event_type`, pick by anger closeness.
4. **Hardcoded absolute fallback** (in Python code, not JSON, so it can never be missing): a
   neutral dry line + no audio (`audio: null`, frontend just shows text). E.g.
   `"ഓ, ഇതും ഒരു error ആണോ."` This must exist so the API never 500s due to an empty library.

### 8.2 Persist after selection

- Update `response_usage` (increment `times_used`, set `last_used_at`, `last_used_session_id`).
- Set `state.last_response_id = chosen.id`.

## 9. EXECUTION ENGINE

```text
def run_user_code(code: str) -> ExecutionResult:
    write code to a temp file (or pass via `python3 -I -c`, isolated mode disables
    site-packages/env pollution — prefer -I)
    subprocess.run(
        ["python3", "-I", "-c", code] or ["python3", "-I", tmp_path],
        capture_output=True,
        timeout=EXEC_TIMEOUT_SECONDS,   # config, suggest 5
        cwd=<isolated tmp dir>,
        env=<minimal env>,
    )
    on subprocess.TimeoutExpired -> ExecutionResult(timed_out=True)
    else -> ExecutionResult(stdout, stderr, returncode, timed_out=False)
```

Safety notes (don't over-engineer for a 6–7hr hackathon, but do the cheap stuff):
- Always use `-I` isolated mode.
- Always enforce the timeout — this is non-negotiable, it's your only defense against `while True: pass`.
- Run from a scratch temp directory, not the project directory, so accidental file writes don't touch your code.
- Truncate stdout/stderr you store/return (e.g. cap at ~4000 chars) to avoid huge payloads from print-spam loops.
- Optional if time allows: `resource.setrlimit` (RLIMIT_CPU, RLIMIT_AS) via `preexec_fn` on Unix for a hard memory/CPU ceiling. Not required for MVP.
- This is a local hackathon demo tool, not a public multi-tenant sandbox — don't spend hours building container-level isolation.

## 11. EVENT ORCHESTRATION (`events.py`)

Central function everything routes through, per AGENTS.md §30:

```text
def process_event(event: Event) -> ProcessedResult:
    state = state_manager.load()
    situations = compute_situations(event, state)          # §5.2
    delta, escape_meta = anger_engine.compute_delta(event, state, situations)  # §7
    new_score = clamp(state.anger_score + delta, 0, MAX_ANGER_SCORE)
    update counters on state (errors/successes/streaks/sessions/escape_attempts)  # §3.1 fields
    response = response_engine.select(event, state, situations)  # §8
    state_manager.save(state)
    events_log.insert(event, anger_before, anger_after=new_score, response.id)
    return ProcessedResult(response, state)
```

Every route handler (`/execute`, `/session/start`, `/excuse`, `/make-it-worse`) is a thin
wrapper: build an `Event`, call `process_event`, serialize the result. This is what keeps
adding new event types (or the optional MAKE_IT_WORSE/EXCUSE features) cheap later.

## 14. WHAT THIS DELIBERATELY DOES NOT DECIDE

- No frontend layout, animation, or visual state machine — that's Stitch's job. The API
  gives you `anger_score`, `anger_level`, `anger_label`, and every counter needed to drive
  whatever UI they build; it doesn't assume how it's rendered.
- The backend *does* resolve which of the 4 named expressions applies (§16), because that
  mapping is simple, deterministic, and needed by any frontend consuming this API — but it
  knows nothing about filenames, image assets, transitions, or animation. It emits a string;
  Stitch decides what to do with it.
- No auth system — deliberately out of scope per the single-memory design in §3.1/§6.1.

## 16. AMMAYI EXPRESSION MAPPING (v1.1 amendment)

Purely presentation-facing. Frontend has exactly 4 static images and needs a string to pick
one. This section adds one derived field to the existing response payload — it does not
touch anger scoring, persistence, execution, classification, session/escape logic, or the
response-selection scoring algorithm in §8.

### 16.1 The four expressions and thresholds

```python
def get_expression(anger_level: int) -> str:
    if anger_level <= 2:
        return "unimpressed"
    elif anger_level <= 4:
        return "disappointed"
    elif anger_level <= 7:
        return "furious"
    else:
        return "done"
```

Note `done` is not "angrier than furious" — per AGENTS.md's performance direction, it's
exhausted/deadpan resignation after prolonged frustration. This is a labeling/vocabulary
distinction only; the derivation is still a plain threshold on `anger_level` (0–8, from §7.1).

**Where it lives**: `response_engine.py`, next to wherever the final response object
(`id`, `text_ml`, `audio`, …) is assembled before being handed back to the route handler.
This is an extension of that existing assembly step, not a new module — there is no
separate "emotion engine."

### 16.2 Resolution order

```text
1. If the selected canonical response has a non-null `expression` field → use it as-is.
2. Otherwise → expression = get_expression(state.anger_level)
```

This is a two-line branch in the same function that already builds the response object —
no new abstraction, no new table.

```python
def resolve_expression(chosen_response: dict, anger_level: int) -> str:
    if chosen_response.get("expression"):
        return chosen_response["expression"]
    return get_expression(anger_level)
```

### 16.3 Test table

```text
anger_level  → expression
0            → unimpressed
1            → unimpressed
2            → unimpressed
3            → disappointed
4            → disappointed
5            → furious
6            → furious
7            → furious
8            → done
10           → done   (anger_level itself is capped at 8 per §7.1, but the
                        function should not assume that cap — no upper guard needed,
                        `else: return "done"` already covers anything > 7 safely)
```

Plus: one test asserting a response with an explicit `"expression": "furious"` override
wins even when `state.anger_level` would otherwise derive `"unimpressed"`.

### 16.4 What does NOT change

- **No new column** on `ammayi_state` or any other table. `expression` is computed at
  response-build time from the already-persisted `anger_level`; it is never written to
  the database. Restarting the server, refreshing, or starting a new session all still
  only persist the fields listed in §3.1 — `expression` simply gets recomputed fresh from
  whatever `anger_level` currently is, which is exactly why it correctly reflects
  Ammayi's memory immediately even across a brand-new session.
- **No change** to `/api/execute`, `/api/session/start`, `/api/excuse`,
  `/api/make-it-worse` request shapes, and no existing response field is renamed or
  removed — `expression` is purely additive inside the existing `ammayi_response` object.
- **No change** to §8's scoring/selection algorithm. Expression resolution happens strictly
  *after* a response has already been chosen.
- `responses.json` entries are not required to set `expression` — it's optional and
  expected to stay `null`/omitted for nearly all lines (see §4 field notes). Only use it
  for the rare line whose performance deliberately doesn't match its anger-level's default
  expression.
